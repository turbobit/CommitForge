# 한글 Atomic Commit 메시지 지침

## 1. 형식

```text
type(scope): 한글 제목

한글 본문

선택적 trailer
```

예:

```text
fix(auth): 만료된 세션의 자동 갱신 실패 수정

- 만료 직전 토큰도 갱신 대상으로 판정하도록 경계 조건을 보완
- 동시 갱신 요청을 단일 작업으로 합쳐 중복 네트워크 호출 방지
- 만료 시각 경계와 동시 요청 시나리오의 회귀 테스트 추가
```

## 2. 제목

- `type`과 `scope`는 소문자 영문
- 제목은 가능한 한 자연스러운 한글
- 전체 제목은 가급적 72자 이내
- 마침표를 붙이지 않음
- 무엇을 했는지보다 왜 필요한 변경인지 드러내는 구체적 표현 사용
- `수정`, `개선`, `추가`, `제거`, `분리`, `통합`, `정리`, `방지` 등의 명확한 서술 사용
- `업데이트`, `변경사항`, `여러 수정`, `코드 개선`처럼 범위가 모호한 표현은 피함
- 서로 다른 목적을 `및`, `그리고`, `/`로 이어 붙이면 분리 여부를 다시 검토

좋은 예:

- `feat(search): 통합 검색에 날짜 범위 필터 추가`
- `fix(session): 토큰 만료 경계에서 갱신이 누락되는 문제 수정`
- `refactor(email): 본문 로딩 책임을 저장소 계층으로 이동`
- `perf(cache): 중복 직렬화를 제거해 응답 생성 비용 절감`
- `build(ios): CocoaPods 의존성을 Swift Package로 전환`
- `docs(api): 재시도 정책과 오류 응답 예시 보강`

나쁜 예:

- `fix: 버그 수정`
- `feat: 여러 기능 추가`
- `chore: 코드 업데이트`
- `feat(auth): 로그인 추가 및 캐시 리팩터링과 문서 수정`

## 3. Scope

scope는 사용자가 변경 위치와 도메인을 빠르게 이해하도록 선택한다.

우선순위:

1. 비즈니스 도메인: `auth`, `email`, `search`, `payment`
2. 패키지/앱: `web`, `mobile`, `api`, `worker`
3. 기술 하위 시스템: `cache`, `db`, `router`, `build`
4. 범위가 명확하지 않거나 전역이면 생략

파일명이나 구현 세부보다 장기적으로 유지되는 도메인 명칭을 선호한다.

## 4. 본문

본문은 diff를 반복 나열하지 말고 변경 의도와 중요한 구현 결정을 설명한다.

권장 구조:

- 변경 배경 또는 해결하려는 문제
- 핵심 동작 변화
- 중요한 구현 방식과 선택 이유
- 영향 범위·호환성·migration
- 수행한 검증

짧고 명확한 변경은 2~4개 bullet이면 충분하다. 복잡한 변경은 문단과 bullet을 조합한다.

반드시 사실만 작성한다.

- 실행하지 않은 테스트를 통과했다고 쓰지 않는다.
- 추론한 성능 효과를 측정 결과처럼 쓰지 않는다.
- diff에 없는 변경을 포함했다고 쓰지 않는다.
- 보안상 안전하다고 단정할 근거가 없으면 검토 범위를 명시한다.

## 5. Breaking Change

호환되지 않는 API, 데이터, CLI, 설정, 프로토콜 변경이 있으면 제목 type 뒤에 `!`를 사용할 수 있다.

```text
feat(api)!: 페이지네이션 응답 형식을 cursor 기반으로 전환
```

본문 마지막에 다음 trailer를 추가한다.

```text
BREAKING CHANGE: 기존 page/size 파라미터를 제거하고 cursor/limit을 사용합니다.
```

Migration 절차가 있으면 함께 명시한다.

## 6. 이슈·공동 작성 Trailer

실제 연관성이 확인된 경우에만 사용한다.

```text
Refs: #123
Fixes: #456
Co-authored-by: 이름 <email>
```

이슈 번호를 추측하지 않는다. 사용자가 요청하지 않은 AI 공동 작성 trailer를 임의로 추가하지 않는다.

## 7. 유형 선택 경계

- 성능이 주목적이면 `perf`, 내부 구조가 주목적이면 `refactor`
- 사용자 동작을 고치면 `fix`, 테스트 기대값만 바로잡으면 `test`
- 의존성/빌드 산출물은 `build`, 일반 저장소 유지보수는 `chore`
- formatting-only는 `style`; formatting과 로직이 섞이면 분리
- 보안 취약점 수정도 사용자 동작의 오류 수정이면 보통 `fix`

## 8. 메시지 자체 검증

커밋 직전 확인:

- 제목이 실제 staged diff 하나의 목적을 정확히 설명하는가?
- 본문이 이유와 영향 범위를 설명하는가?
- 한글이 자연스럽고 과장되지 않았는가?
- type/scope가 일관적인가?
- Breaking Change가 누락되지 않았는가?
- 실행한 검증만 기록했는가?
