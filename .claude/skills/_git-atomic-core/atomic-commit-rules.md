# Atomic Commit 규칙

## 1. 목표

Atomic Commit은 단순히 파일 수가 적은 커밋이 아니다. 하나의 독립적인 의도를 완결된 형태로 기록하는 커밋이다.

각 커밋은 다음 질문에 모두 `예`여야 한다.

1. 제목을 접속사 없이 하나의 문장으로 설명할 수 있는가?
2. 이 커밋만 독립적으로 `cherry-pick`해도 논리적으로 성립하는가?
3. 이 커밋만 `revert`해도 다른 변경을 불필요하게 되돌리지 않는가?
4. 변경 이유와 영향 범위를 diff만으로 이해할 수 있는가?
5. 가능한 범위에서 빌드·타입 검사·테스트가 통과하는 중간 상태인가?
6. 기능 추가, 버그 수정, 리팩터링, 포맷팅 등 서로 다른 의도가 섞이지 않았는가?

하나라도 아니면 분리 또는 재그룹화한다.

## 2. 기본 분류

변경의 주된 의도에 따라 다음 Conventional Commit type을 사용한다.

- `feat`: 사용자 또는 호출자가 사용할 수 있는 기능 추가
- `fix`: 잘못된 동작, 예외, 회귀, 오류 수정
- `refactor`: 외부 동작을 의도적으로 바꾸지 않는 구조 개선
- `perf`: 측정 가능하거나 명확한 성능 개선
- `test`: 제품 코드 동작 변경 없이 테스트만 추가·수정
- `docs`: 문서만 변경
- `style`: 포맷, 공백, import 정렬처럼 의미 없는 코드 스타일 변경
- `build`: 빌드 시스템, 패키징, 의존성 선언/잠금
- `ci`: CI/CD 설정
- `chore`: 위 유형에 속하지 않는 유지보수
- `revert`: 기존 커밋 되돌림

한 커밋에 여러 type이 필요해 보이면 대체로 분리 대상이다. 단, 구현을 완결하는 데 필수적인 테스트·타입·설정은 주된 type 커밋에 함께 포함할 수 있다.

## 3. 함께 유지해야 하는 변경

다음은 분리하면 중간 상태가 깨질 가능성이 높으므로 원칙적으로 함께 둔다.

- 구현과 그 구현의 직접적인 회귀 테스트
- 공개 API 변경과 모든 필수 호출부 수정
- 타입/스키마 정의와 이를 사용하는 최소 구현
- DB migration과 해당 스키마를 소비하는 코드
- UI 구조와 그 UI가 정상 표시되는 데 필수적인 스타일
- 패키지 manifest와 그 변경으로 생성된 lockfile
- 직렬화 형식 변경과 읽기/쓰기 양쪽 호환 코드
- 프로토콜 변경과 양 끝점의 필수 수정
- 파일 rename/move와 동일 커밋 없이는 깨지는 import 경로 수정
- 기능 플래그 추가와 기본값·구성 로딩 코드

테스트가 구현 의도를 설명하고 회귀를 방지한다면 구현과 함께 둔다. 테스트 프레임워크 정리나 광범위한 테스트 리팩터링은 별도 커밋으로 분리한다.

## 4. 분리해야 하는 변경

다음은 의미가 다르므로 가능한 경우 반드시 분리한다.

- 순수 rename/move와 기능 변경
- 포맷팅과 로직 변경
- 동작 보존 리팩터링과 새 기능
- 기존 버그 수정과 별개의 기능 추가
- 의존성 업그레이드와 무관한 애플리케이션 변경
- 문서 오탈자 수정과 제품 코드 변경
- 여러 독립 기능 또는 여러 독립 버그 수정
- 디버그 로그 제거와 별개의 구현 변경
- 코드 생성 결과 갱신과 생성기 자체의 별개 변경
- 여러 패키지에 걸친 서로 독립적인 수정
- 데이터 migration과 무관한 데이터 정리
- 보안 hardening과 독립적인 UX 개선

## 5. 과도한 분리 방지

다음처럼 기술적 단계만을 이유로 쪼개지 않는다.

- 타입만 먼저 추가하고 다음 커밋에서 즉시 구현하는 경우
- 한 기능의 모델, 서비스, UI를 각각 기계적으로 분리하는 경우
- 테스트가 실패하는 중간 커밋을 만드는 경우
- 한 줄씩 또는 파일별로 무의미하게 분리하는 경우
- 동일한 원인과 동일한 검증으로 설명되는 수정들을 억지로 나누는 경우

파일 수가 많아도 하나의 의도를 완결하면 한 커밋일 수 있다. 파일 수가 하나여도 여러 의도가 섞이면 hunk 단위로 나눌 수 있다.

## 6. 커밋 순서

다음 우선순위는 절대 규칙이 아니라 의존성 그래프를 위한 기본값이다.

1. 독립적인 rename/move 또는 기계적 정리
2. 이후 변경의 전제가 되는 동작 보존 리팩터링
3. 기반 타입·인터페이스·스키마·설정
4. 기능 또는 버그 수정
5. 독립적인 테스트 인프라 개선
6. 독립적인 성능 개선
7. 문서
8. 포맷팅·정리

단, 각 중간 커밋이 논리적으로 성립해야 한다. 기반 타입만 추가하면 빌드가 깨지는 경우 구현과 합친다. migration을 먼저 적용하면 구버전 코드가 깨지는 경우 호환 단계 또는 단일 커밋으로 구성한다.

## 7. 의존성 그래프 판단

각 후보 커밋 A와 B에 대해 다음을 확인한다.

- B가 컴파일되거나 실행되기 위해 A가 필요한가?
- B의 테스트가 A 없이는 의미가 없는가?
- B가 A에서 추가한 타입·API·스키마를 사용하는가?
- A를 되돌리면 B도 반드시 되돌려야 하는가?

의존한다면 `A → B` 순서로 둔다. 양방향 의존이 강하면 한 커밋으로 합친다.

## 8. staged 변경 존중

기존 staged 상태는 사용자의 의도 신호다.

- 먼저 `git diff --cached`를 별도로 분석한다.
- staged 변경이 이미 하나의 atomic unit이면 우선 커밋 후보로 유지한다.
- staged와 unstaged가 같은 파일에 섞여 있으면 `git add <file>`로 덮어쓰지 않는다.
- staged 구성이 비원자적이면 스냅샷이 확보된 뒤 index만 재구성할 수 있다.
- working tree 내용은 staging 재구성을 위해 수정하지 않는다.
- 실패 시 기존 staged 상태를 자동으로 추측 복구하지 말고 스냅샷 위치와 복구 방법을 보고한다.

## 9. 특수 파일

### Lockfile

manifest와 lockfile은 같은 의존성 변경이면 함께 커밋한다. lockfile의 대규모 변경이 manifest와 설명되지 않으면 원인을 조사한다.

### Generated file

생성 결과가 소스와 함께 버전 관리되는 프로젝트라면 생성기/원본과 함께 둔다. 생성 명령과 무관한 광범위한 재생성은 분리하거나 중단한다.

### Migration

migration, 모델, 쿼리, 롤백/호환 코드의 관계를 확인한다. 배포 순서가 중요한 경우 본문에 명시한다.

### Submodule

submodule 포인터 변경은 내부 커밋이 존재하고 접근 가능한지 확인한다. 다른 코드 변경과 독립적이면 별도 `build` 또는 `chore` 커밋으로 둔다.

### Git LFS

LFS pointer와 실제 객체가 정상인지 확인한다. 바이너리 파일을 일반 Git blob으로 실수로 추가하지 않았는지 확인한다.

### 대용량·바이너리

목적, 크기, 생성 출처를 확인한다. Diff로 검증할 수 없으므로 관련 메타데이터와 소비 코드가 필요하면 함께 둔다.

## 10. 모노레포

- package 경계를 기본 scope 후보로 사용한다.
- 여러 package를 관통하는 API 변경은 한 원자적 변경일 수 있다.
- 독립 배포 package의 변경은 가능한 분리한다.
- 공통 라이브러리 변경과 소비자 변경이 하위 호환이면 분리할 수 있다.
- 하위 호환이 아니면 깨지지 않는 전환 단계 또는 단일 커밋으로 구성한다.
- workspace lockfile은 실제 manifest 변경과 함께 둔다.

## 11. 최종 판단 문장

각 커밋 직전에 다음 문장을 완성한다.

> 이 커밋은 **[하나의 목적]**을 위해 **[변경 범위]**를 변경하며, 독립적으로 적용·되돌릴 수 있고 **[검증]**으로 확인했다.

문장을 자연스럽게 완성하지 못하면 staging을 다시 구성한다.
